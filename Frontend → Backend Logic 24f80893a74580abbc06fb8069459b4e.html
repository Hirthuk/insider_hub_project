API Configuration setup

api.js file configuration explanation

what is config object used in the interceptors

What is config?

  • In Axios, every request you make (apiClient.get(...), apiClient.post(...), etc.) starts as a configuration object.
  • This config is built by Axios from:
    1. The defaults you set in axios.create({...})
    1. The arguments you passed to .get() / .post() / etc.
    1. Any modifications made by request interceptors.

Think of config as the blueprint for the HTTP request:

{
  url: '/api/auth/login',       // path relative to baseURL
  baseURL: 'http://localhost:8080',
  method: 'post',
  headers: {
    'Content-Type': 'application/json',
    Authorization: 'Bearer <token>' // added by your interceptor
  },
  data: { sapid: '...', password: '...' },
  timeout: 10000
}

Why do we return config?

  • The request interceptor is literally a function that Axios calls before sending the request.
  • Axios expects you to return the (possibly modified) config so it knows what to send.
  • If you don’t return it, Axios won’t have the complete request details and the request won’t proceed.
  • Returning config hands the finalized blueprint back to Axios so it can execute the request with your changes.

How it’s used in every request

Here’s the flow:

  1. You call:
    apiClient.get('/users')
  1. Axios internally creates the config object:
    {
  baseURL: 'http://localhost:8080',
  url: '/users',
  method: 'get',
  headers: { 'Content-Type': 'application/json' }
}
  1. The request interceptor runs before the request is sent:
    • Reads the token from localStorage.
    • If found, sets:
      config.headers.Authorization = `Bearer ${token}`
    • Logs the URL.
    • Returns the updated config.
  1. Axios takes the returned config and actually performs the HTTP request.
  1. The response (or an error) goes through the response interceptors before you see it.

Simple analogy

Imagine config as a pizza order slip:

  • You start with the defaults (Cheese Pizza — baseURL, headers).
  • You add some extras in your .get() / .post() call (Extra Olives — data, params).
  • The request interceptor is the chef checking every slip and saying:
    “Oh, this is a VIP customer (has token), add free extra cheese (Authorization header)!”
  • Then the slip is handed back to the kitchen (Axios core) to bake the pizza (make the request).

Interceptor function

Exactly ✅ —

apiClient.interceptors.request.use() expects two arguments:

apiClient.interceptors.request.use(
  requestSuccessHandler, // runs before request is sent
  requestErrorHandler    // runs if request config building fails
);

In your case:

(config) => { ... }

is the requestSuccessHandler — an arrow function that receives the Axios config object before the request goes out.

  • Axios automatically passes that config into your function.
  • You then modify it (like adding Authorization) and return it.

So the real shape is:

apiClient.interceptors.request.use(
  // success handler
  (config) => {
    // modify config here
    return config; // must return so Axios can continue
  },

  // error handler (optional)
  (error) => {
    return Promise.reject(error);
  }
);

💡 If you don’t return config in the first function, Axios won’t know how to proceed and the request will never be sent.

Promise rejct

Alright — let’s break that down slowly because it’s a core JavaScript + Axios concept.

1️⃣ What Promise.reject(error) does

  • In JavaScript, Promises represent something that will finish later (async).
  • If something goes wrong, you can make the Promise fail (reject) instead of succeed (resolve).
  • Promise.reject(error) is basically saying:
    "This async operation failed — here’s the reason (error)."

2️⃣ Why it’s used in Axios interceptors

When you have:

(error) => {
  console.error('Request error:', error);
  return Promise.reject(error);
}

It means:

  • If Axios encounters an error before sending the request (e.g., invalid config, interceptor failure),

    this function will be called.

  • We log the error.
  • Then we return Promise.reject(error) to pass that error back to wherever .get() / .post() was called.

Without this, Axios wouldn’t know to tell your calling code that something went wrong.

3️⃣ Flow example

Let’s say you have:

apiClient.get('/users')
  .then(response => console.log('Data:', response))
  .catch(error => console.error('Caught in .catch:', error));
  • If the request config fails in the request interceptor:
    • Your error handler (error) => { ... } runs.
    • Promise.reject(error) is returned.
    • The .catch(...) in your calling code receives that error.

4️⃣ Analogy

Think of it like throwing an error but in async style:

throw error; // sync world
Promise.reject(error); // async world

If you didn’t return Promise.reject(error),

Axios would think “oh, I got something else back, maybe it’s fine” — and your .catch() wouldn’t be triggered properly.

1. Importing Axios

import axios from 'axios';
  • Pulls in the axios HTTP client library.
  • axios lets you make API calls easily (GET, POST, etc.) and supports features like interceptors for request/response customization.

2. API Configuration

export const API_CONFIG = {
  BASE_URL: import.meta.env.VITE_API_BASE_URL || 'http://localhost:8080',
  ENDPOINTS: {
    LOGIN: '/api/auth/login',
    LOGOUT: '/api/auth/logout',
    REFRESH_TOKEN: '/api/auth/refresh',
  }
};
  • BASE_URL is pulled from your .env file variable VITE_API_BASE_URL.
    • import.meta.env is how Vite accesses environment variables.
    • If .env doesn't have VITE_API_BASE_URL, it defaults to 'http://localhost:8080'.
  • ENDPOINTS is just an object holding the paths for login, logout, and refresh so you don’t hardcode them multiple times in the app.

3. Creating an Axios instance

export const apiClient = axios.create({
  baseURL: API_CONFIG.BASE_URL,
  timeout: 10000, // 10 seconds timeout
  headers: {
    'Content-Type': 'application/json',
  },
});
  • axios.create() makes a custom Axios instance with default settings:
    • baseURL → all requests will be relative to this.
    • timeout → if the request takes longer than 10 seconds, it will fail.
    • headers → sets default request header to application/json.

4. Request Interceptor

apiClient.interceptors.request.use(
  (config) => {
    const token = localStorage.getItem('authToken');

    if (token) {
      config.headers.Authorization = `Bearer ${token}`;
    }

    console.log('Making request to:', config.url);
    return config;
  },
  (error) => {
    console.error('Request error:', error);
    return Promise.reject(error);
  }
);
  • Interceptors let you run code before each request.
  • config is the request configuration object (URL, method, headers, etc.).
  • Gets authToken from localStorage.
  • If the token exists, adds an Authorization header:
    Authorization: Bearer <token>

    This is how the backend verifies who you are.

  • Logs the request URL for debugging.
  • If something fails during request setup, it logs and rejects the request.

5. Response Interceptor

apiClient.interceptors.response.use(
  (response) => {
    console.log('Response received:', response.status);
    return response;
  },
  (error) => {
    console.error('Response error:', error.response?.status, error.response?.data);

    if (error.response?.status === 401) {
      localStorage.removeItem('authToken');
      localStorage.removeItem('userRole');
      localStorage.removeItem('userSapId');
      localStorage.removeItem('isAuthenticated');

      if (window.location.pathname !== '/login') {
        window.location.href = '/login';
      }
    }

    return Promise.reject(error);
  }
);
  • This runs after every response from the server.
  • On success:
    • Logs the HTTP status (e.g., 200 OK).
    • Passes the response back to your calling code.
  • On error:
    • Logs the status code and error data from the server.
    • If status is 401 (Unauthorized — usually means token expired or invalid):
      • Clears authentication-related data from localStorage (authToken, userRole, etc.).
      • Redirects the user to /login unless they’re already on the login page.
  • Promise.reject(error) sends the error back so the calling code can handle it if needed.

In short — What’s happening

  1. Setup:
    • Define a reusable apiClient with your API base URL, headers, and timeout.
  1. Before request:
    • Always check if authToken exists in localStorage.
    • If yes, attach it to the Authorization header.
  1. After response:
    • If response is good → just return it.
    • If it’s a 401 → token is probably bad/expired:
      • Wipe all stored auth data.
      • Redirect to login so the user can reauthenticate.
