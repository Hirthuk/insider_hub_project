Backend Workflow with files

High-level flow

  • Frontend calls /api/auth/login with credentials (sapid + password).
  • Backend verifies credentials against Neon (Postgres) and issues a signed JWT with role claim.
  • Frontend stores the JWT and sends it in Authorization: Bearer <token> for protected endpoints.
  • A JWT filter validates the token on every request and sets the user + role into Spring Security’s context.
  • @PreAuthorize("hasRole('ADMIN')") checks the role and allows/denies controller methods.
  • Controllers delegate to services; services use repositories to operate on the database.
  • Errors are returned uniformly via @ControllerAdvice.

Detailed flow, step-by-step

  1. App startup and configuration
  • Spring Boot auto-configures:
    • DataSource (Hikari) to Neon using application.properties.
    • JPA/Hibernate scans your @Entity (UsersEntity) and repositories.
    • Web layer with embedded Tomcat.
    • Security via your SecurityConfig.
  • SecurityConfig does:
    • Disables CSRF (stateless APIs).
    • Permits /api/auth/login (public).
    • Requires authentication for all other endpoints.
    • Registers JwtAuthFilter before UsernamePasswordAuthenticationFilter.
    • Enables @PreAuthorize with @EnableMethodSecurity.
  1. Database model (JPA)
  • UsersEntity represents the users table with validations and constraints:
    • email (unique), password (hashed), role (USER/ADMIN), sapid (unique), etc.
    • creation_date auto-set with @PrePersist.
    • Use wrapper types (Integer, Long) for nullable fields.
  • UserRepository extends JpaRepository: findAll, save, findBySapid, findByEmail, deleteBySapID.
  1. Login: issuing the JWT

    Endpoint

  • POST /api/auth/login
  • Body: { "sapid": 52006992, "password": "mypassword123" }

AuthService.login flow

  • Read sapid + password from request DTO.
  • Look up user by sapid: userRepository.findBySapid(sapid).
  • Compare raw password with stored hash using BCrypt:
    • passwordEncoder.matches(raw, hashedFromDb)
  • If matched:
    • Build JWT via JwtUtil.generateToken(sapid, role):
      • Claims: subject = sapid as string, role = ADMIN/USER, iat, exp.
      • Signed with a server-side SecretKey (HS256).
    • Return {"role": "...", "token": "..."}.
  • If not matched → throw BadCredentialsException (handled by @ControllerAdvice → 401).
  • If sapid not found → ResourceNotFoundException → 404.

JwtUtil details

  • SECRET_KEY = Keys.secretKeyFor(SignatureAlgorithm.HS256) (kept in memory for now).
  • generateToken:
    • setClaims({ role }), setSubject(sapid), setIssuedAt, setExpiration.
    • signWith(secret, HS256).
  • extractAllClaims(token): parseClaimsJws(token).getBody()
  • isTokenExpired(token): checks expiration claim.
  1. Sending protected requests with the token
  • Frontend stores the token from login.
  • For protected endpoints (e.g., POST /api/users, GET /api/users), include header:

    Authorization: Bearer <token>

  1. JwtAuthFilter: authenticating each request
  • Runs once per request (OncePerRequestFilter).
  • Reads Authorization header, extracts token.
  • Validates and parses claims using JwtUtil:
    • subject → sapid (string)
    • role → ADMIN or USER
  • Builds a Spring Authentication object:
    • UsernamePasswordAuthenticationToken(subject, null, [new SimpleGrantedAuthority("ROLE_" + role)])
  • Places it into SecurityContextHolder.
  • If invalid/expired/missing token: no auth set → protected endpoints will be denied later.
  1. Authorization at controller methods
  • Your controller methods are annotated with:

    @PreAuthorize("hasRole('ADMIN')")

  • When invoked, Spring checks the current user’s authorities from SecurityContext:
    • If contains ROLE_ADMIN → proceed.
    • Else → AccessDeniedException → 403 (handled by @ControllerAdvice).
  1. Controller → Service → Repository → DB
  • UserController:
    • GET /api/users → userService.getAllUsers()
    • POST /api/users → @Valid payload → userService.createUser(user)
    • DELETE /api/users/{sapid} → userService.deleteUser(sapid)
  • UserService:
    • createUser:
      • checks duplicate sapid, hashes password via BCrypt, saves via repository.
    • deleteUser:
      • checks existence, deletes by sapid.
  • Repository:
    • JPA generates SQL to Neon via Hikari/Hibernate.
  • Responses:
    • Success → normal JSON body (e.g., created user).
    • Failures → exceptions handled by @ControllerAdvice as structured ApiError.
  1. Global exception handling (@ControllerAdvice)
  • Converts exceptions to consistent JSON with status codes:
    • BadCredentialsException → 401 Unauthorized
    • AccessDeniedException → 403 Forbidden
    • NotFoundException → 404 Not Found
    • ConflictException → 409 Conflict (duplicates, etc.)
    • MethodArgumentNotValidException → 400 Bad Request with field-level errors
    • Fallback → 500 Internal Server Error

Security essentials and conventions

  • Role handling:
    • Your JWT stores role as ADMIN/USER.
    • Filter wraps it as authority "ROLE_ADMIN" or "ROLE_USER".
    • @PreAuthorize("hasRole('ADMIN')") expects that "ROLE_" prefix implicitly.
  • Token scope:
    • Stateless: no server sessions are stored; every request must have a valid token.
    • Expiration: enforced by isTokenExpired() check.
  • Passwords:
    • Always store BCrypt hashes; never store plaintext; always verify using matches().

Tracing a real request (example)

  • Login:
    • Client: POST /api/auth/login {sapid, password}
    • DB: find user, verify hash
    • Server: return JWT {"token", "role"}
  • Create user:
    • Client: POST /api/users with Authorization: Bearer <token> + JSON body
    • Filter: validates token, sets SecurityContext with ROLE_ADMIN
    • PreAuthorize: hasRole('ADMIN')? Yes → proceed
    • Controller → Service:
      • hash password for the new user, save in DB
    • Return created user

Common pitfalls to watch

  • Role mismatch: must use "ROLE_" prefix in authorities.
  • Token expired: renew via login.
  • Primitive types in entities for nullable columns: use Integer/Long instead of int/long.
  • Missing @EnableMethodSecurity → @PreAuthorize won’t run.
  • Wrong Authorization header: must be exactly "Bearer <token>".

Cheat sheet of main classes and their duties

  • UsersEntity: DB model + validations + schema mapping.
  • UserRepository: DB access (CRUD + findBySapid/findByEmail).
  • UserService: business logic (hashing, duplicate checks, delete rules).
  • UserController: REST endpoints for users, admin-protected.
  • AuthService/AuthController: login, issue JWT.
  • JwtUtil: create/parse/validate tokens.
  • JwtAuthFilter: extract token from header, set SecurityContext with authorities.
  • SecurityConfig: defines public/protected routes, installs JWT filter, enables method security.
  • GlobalExceptionHandler: consistent JSON errors and status codes.
